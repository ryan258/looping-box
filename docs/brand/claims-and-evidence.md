## Evidence strength and editorial review

1. **Product behavior.** Check the current code, configuration, and operator docs before reusing a behavioral claim. Give the supported condition and adjacent limitation where it changes what the reader should do. Keep “offline by default” and the optional-provider disclosure together when describing data handling.
2. **Demonstrated behavior.** Label fixture expectations and recorded runs accurately. Include the date, revision or working-tree description, Python/OS, commands, and fixture source. Three recorded free-router examples each produced a draft and reported zero cost. The current automatic log path was exercised with simulated provider responses, including failures and unavailable cost. [Recorded examples](collateral/openrouter-example-transcript.md) · [Review status](../../REVIEW.md#current-checkout-demonstrations)
3. **Recorded acceptance.** [Review status](../../REVIEW.md#remaining-acceptance-work) records an earlier macOS Python 3.14.7 offline suite pass (301 tests with one skip), an isolated installed-wheel pass (two tests), and a Ruff pass. [Acceptance evidence](../../acceptance-results.md#recorded-operator-evidence) records the operator results and preserves earlier failures. The current worktree contains later runtime changes. Some older sections in the evidence file still describe the historical pass as pending. Linux and CI matrix results, manual real-terminal acceptance, and current-tree release acceptance have no recorded result in this audit.
4. **Evaluation and comparison.** Record observations against a known fixture or revision. Attribute user feedback only with permission. A walkthrough demonstrates a specified workflow. To claim accuracy, time savings, accessibility conformance, or relative performance, obtain evidence designed for that claim.
5. **Release and legal claims.** Ryan owns the license, public availability, and the decision to send or publish anything. Update candidate language and the destination only when those facts change. Route requests for regulated, security-critical, or organizational use back to the documented single-operator threat model and scope before making any commitment.

## Wording that changes the claim

| If the draft says… | Replace it with… |
| --- | --- |
| “AI summarizes your inbox offline” | “The offline draft assembles short excerpts and shows their source paths.” |
| “Blocks every risky action” | “Holds files that match configured review terms. Looping Box’s workflow ends at local drafting.” |
| “Approved to deploy” | “Approved for local drafting.” |
| “Private and air-gapped” | “Offline by default. Enabled model roles send data to the configured endpoint.” |
| “Tamper-proof audit trail” | “Hash-linked local logs can flag changed entries and broken links.” |
| “Verified identity” | “Records the configured approver name and a signed local decision.” |
| “No work is ever lost” | “Retains local evidence for inspection and documented recovery.” |
| “Enterprise-ready,” “compliant,” or “certified accessible” | Name the exact feature and its supported environment. Leave the assurance claim out pending appropriate evidence. |
| “Try it free” or “Install from PyPI” | Use “See the offline walkthrough” for a permitted demonstration. Announce a download or terms after the owner confirms them. |
| “All model calls are logged” | “The numbered example launcher saves a local run record when you use `--free`.” |
| “Free model calls always report zero cost” | “The free example mode uses `openrouter/free`. The saved record shows OpenRouter’s reported cost when available.” |

## Roadmap and research language

Voice-friendly queue navigation, prompt preview and redaction, more formats, and stronger recovery are proposals. The broader loop experimentation workbench is also a proposal. Describe them as research topics when discussing future direction. An approval service, agent execution, continuous watching, a GUI, shared-team accounts, and commercial support are outside the current offer.
